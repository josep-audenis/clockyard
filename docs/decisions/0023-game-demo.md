# 0023. The game demo: Catch on the reference CPU

- Status: Accepted
- Date: 2026-11-14
- Depends on: ADRs 0019 (the reference CPU), 0020 (Phase 5 plan,
  increment 3), 0021 (devices), 0022 (memory-mapped I/O)

## Context

ADR 0020 makes the game demo the third Phase 5 increment: a small game on
the reference CPU, chosen only once devices and memory-mapped I/O work.
They now do (ADRs 0021 and 0022). The brief's aspirational demo is "a small
game running on a processor designed inside Clockyard", and it warns
against committing to a game or an instruction set too early. ADR 0020
adds that a richer CPU waits until a game shows what is missing.

So the game should fit the machine as it is (`docs/reference-cpu.md`):

- **Instructions:** load, store, add and subtract (immediate or from a
  data address), `JMP`, `JZ`, `JC`, `OUT`, `HLT`. There is no `AND`,
  `OR` or shift, no subroutine call, and no indirect RAM access.
- **Memory:** a 256-word program ROM and 240 bytes of RAM.
- **Devices:**
  - `KEY` is the one key held, not a set of keys.
  - The screen is 64 × 32 pixels, reached a byte at a time through `SPTR`
    and `SDATA`, and readable back.
  - `HEX` shows a byte on two digits.
- **Speed:** each instruction takes two cycles. Phase 4 measured about
  9,950 cycles per second at the 10,000 setting, before the I/O parts
  were added: roughly 5,000 instructions a second.

Without bit operations, a program can only write whole bytes. A screen
byte is 8 pixels wide and 1 pixel tall. So a game whose objects are
byte-wide bars that move a whole byte sideways, or one row up or down,
looks natural. One that needs single pixels or square cells does not.

## Decision

1. **The game is Catch.** Blocks fall down the screen, one at a time, in
   one of 8 lanes (the 8 bytes of a row). The player moves a paddle along
   the bottom row with the arrow keys:
   - **Catch:** a block that lands on the paddle scores a point. The score
     is shown on `HEX`, and the next block falls a little faster.
   - **Miss:** a block that lands anywhere else ends the game with `HLT`.
     *Run until* Halted then stops the run, and the status bar says so
     (ADR 0021).
   - **Again:** Reset starts a new game.
2. **Pictures:**
   - A block is a short bar (`0x3C`) falling one pixel row per step.
   - The paddle is a full byte (`0xFF`) in row 31. Left and right move it
     one lane, and it stops at the edges.
3. **It uses the devices as ADR 0022 meant:**
   - The paddle is moved by `KEY`: Left `0x82`, Right `0x83`, held for
     repeated moves.
   - Drawing goes through `SPTR` and `SDATA`.
   - A landing is decided by reading the screen back: a block reaching
     row 31 reads `SDATA` there, and the paddle's byte is not 0. What
     is on the screen decides, not a comparison of lane numbers.
4. **No new instructions.**
   - The program fits the ROM with room to spare. A sketch of it is about
     100 words. *As built (step 1):* 89 words.
   - The block's lane comes from a counter that changes as the game runs.
     The engine is deterministic, so the same keys at the same cycles
     always give the same game. *As built (step 1):* the counter adds 5
     lanes, modulo 8, per block, so the lanes come in a fixed order that
     visits all 8. It does not depend on the keys.
   - What the game shows to be missing is listed in the roadmap for a
     later "richer CPU" ADR: bit operations for single pixels, and a call
     for shared drawing code.
5. **The first block falls in the paddle's lane.** The first point then
   needs no timing from the player. The demo and Playwright can rely on it
   without racing the clock. Later lanes follow the counter.
6. **Speed:**
   - The game is paced by a delay loop and tuned for the top speed setting
     (10,000).
   - Step 1 measures the CPU's speed again with the I/O parts, as ADR 0019
     did. If the editor no longer keeps up, the delay is tuned to the
     measured speed. *Measured (step 1):* about 10,000 cycles per second
     at the 10,000 setting (the dev build in the browser, the cycle
     counter read 5 s apart while running), so the delay stays as tuned.
     A block takes about 3 s to fall at first.
   - Slower settings slow the game; the docs say which speed to use.
7. **It ships as its own example, `catch.clockyard.json`.**
   - It is generated by `scripts/reference-cpu.mjs` from the same circuit,
     with the game in the ROM.
   - `reference-cpu` keeps "draw the key held".
   - Both files are regenerated together and checked by `--check`.
8. **Order of work.** Each step is one pull request:
   1. The rules in `docs/reference-cpu.md`, next to its other example
      programs; the program in the generator; and native tests.
      *As built:* the program is `scripts/catch.asm`, which the native
      tests include and step 2's generator will read.

      The tests run the game on the circuit and the model together with
      scripted keys:
      - a caught block scores and speeds up the fall;
      - the paddle stops at both edges;
      - a missed block halts;
      - Reset starts again.

      The speed is measured.
   2. The `catch` example, Playwright and docs:
      - Run, the first block is caught and `HEX` shows 1;
      - holding an arrow moves the paddle on the screen;
      - a miss stops the run with "Stopped: LED Halted lit".

      This closes the increment.

## Alternatives considered

- **Snake.** It is the best-known small game, and it could use the screen
  as its memory: each body byte would hold the direction to the next one,
  so the tail could follow it without a queue in RAM, which the CPU cannot
  index. But square cells need four bytes each, drawn and erased with
  repeated code (there is no call). That puts it near the 256-word ROM,
  and wrapping or walls need extra bookkeeping. It is a good later
  challenge, or a test of a richer CPU.
- **Breakout.** Bricks as bytes suit the screen, and reading `SDATA` finds
  hits. But a ball moving diagonally a byte sideways per row looks jumpy,
  and its bounce rules double the code of Catch. It is worth trying once
  Catch works.
- **Pong for two players.** `KEY` is one key, so two players cannot each
  hold one. A one-player version is Breakout without the bricks.
- **Adding instructions first** (bit operations, indirect addressing, a
  call). That would make the game easier to write, but ADR 0020 says the
  game should show what is missing before the instruction set grows.

## Consequences

- The aspirational demo becomes concrete and small. Two steps, as in
  increment 2.
- The game is real software on the user-visible CPU: its blocks, paddle
  and score come from instructions executing on simulated parts, with no
  hidden logic (CLAUDE.md).
- A game run in real time is hard to test by timing keys. Item 5 and the
  scripted native tests avoid that; Playwright checks only outcomes that
  do not depend on when a key lands.
- The generator writes two examples, so a change to the CPU circuit
  reaches both at once.
- What the game lacks (single pixels, shared drawing code) becomes the
  input to any richer-CPU ADR, as ADR 0020 intended.
