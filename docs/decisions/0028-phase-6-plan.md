# 0028. Phase 6: what comes after the Phase 5 plan

- Status: Accepted; increment 4's target amended by ADR 0034
- Date: 2026-11-16
- Depends on: ADR 0020 (the Phase 5 plan, now built); ADRs 0021–0027

## Context

The seven increments of ADR 0020 are built:
- devices;
- memory-mapped I/O;
- the Catch game;
- sharing by link;
- challenges 1 to 9;
- waveforms;
- examples with notes, and components added from other files.

The brief's phases end at Phase 5, whose features are listed as
*potential*. Its other sections, and what earlier ADRs deferred, still
leave work:

- **Storage.** Brief §7 lists for "later":
  - an IndexedDB project library;
  - autosave;
  - project previews;
  - recent projects;
  - backup.

  None exists. Work is lost on a reload unless it was exported. ADR 0025
  left challenge progress waiting for local storage, and ADR 0027 left a
  component library kept in the browser waiting for it too.
- **Performance.** Brief §9 and §10 ask for repeatable benchmarks of
  cascaded gates, high fan-out, large combinational circuits, registers,
  counters and repeated steps. It names circuits of "thousands or tens of
  thousands of components" as a goal to be measured.

  Today there is one measurement: the reference CPU's run speed (ADR 0019,
  ADR 0026). Nothing measures loading, editing or drawing a large circuit.
- **Editing while running.** Every connectivity edit resets registers,
  RAM and time (ADR 0017, a rough edge on the roadmap). A design that has
  run for a while is lost by moving a wire. Recordings are lost too, since
  waveforms restart with every load (ADR 0026).
- **Challenges 10 to 12** wait for their own ADR (ADR 0025): build a
  programmable CPU, run a program on it, connect an output device. Each
  needs a bench that drives a CPU.
- **Signals.** Values are two-state (ADR 0006, ADR 0014). Brief §5.1 asks
  the architecture to allow four-state logic (`X`, `Z`) later, with
  explicit rules for several drivers. Today an `X` would show the loops
  that do not settle, and `Z` would allow shared buses, which a CPU built
  by hand will want.
- **A richer CPU.** Catch showed what the reference CPU lacks (ADR 0023):
  - bit operations, to draw single pixels;
  - a call and return, to share code.

  The brief said not to commit to an instruction set before the earlier
  phases were sound. They are now, and a game has shown what is missing.
- **Smaller rough edges**, listed on the roadmap:
  - a file opens in the current view;
  - routing does not avoid label tags;
  - Make component can cover parts below it;
  - the screen-reader readout skips registers and screens;
  - the waveform panel is cramped on narrow windows.

## Decision

1. **Phase 6 is a project phase, not one from the brief,** run as Phase 5
   was. It is split into increments, each with its own ADR, its own target
   that works in the browser and in tests, and steps of one pull request
   each. The roadmap lists them and marks each one done.
2. **The order:**
   1. **Local persistence.** Projects are kept in the browser (IndexedDB)
      with autosave, a list of recent projects, and a component library
      that *Add components* can read.
      - Nothing leaves the browser.
      - Export and links stay the way to move work elsewhere.
      - Challenge progress is kept here.
      - Target: edit a circuit, reload the page, and it is back; a
        component saved to the library is added to another project.
   2. **Benchmarks.**
      - Reproducible benchmark circuits, generated by a script as the
        examples are: a long gate chain, high fan-out, a wide ripple
        adder, banks of counters, and the reference CPU, each scaled to
        thousands and tens of thousands of parts.
      - They are measured natively and in the browser: load, settle, tick,
        an edit's reload, and the canvas frame time.
      - Results go in a document with the machine they ran on.
      - The increment optimizes only what the numbers show is too slow,
        against targets set from the first measurement.
      - Target: the largest benchmark opens, runs and can be edited at
        the speeds the document records, and a regression check keeps them.
   3. **Editing a running circuit.**
      - An edit keeps the state of every flip-flop and memory whose part
        still exists, and keeps time and the waveform record, instead of
        starting again from Reset.
      - Its rules are the engine's. The editor sends the edit, as it does
        today.
      - The smaller rough edges that touch the same code come with it:
        opening a file to fit its circuit, and the readout covering
        registers.
      - Target: the 8-bit counter, run to some value, keeps counting from
        it after a wire is moved.
   4. **Challenges 10 to 12.**
      - A bench with its own ROM, RAM and output device, wired to a CPU's
        address and data pins as ADR 0025 sketched.
      - The checks are test programs whose results are read from memory
        or the device.
      - Target: the reference CPU, as a solution, passes all three.
   5. **Four-state signals.**
      - `X` and `Z` in the engine.
      - A rule for several drivers on one net, written in
        `docs/simulation-model.md` before any code.
      - A tri-state buffer part.
      - Loops that do not settle show `X` rather than only a diagnostic.
      - This comes after the benchmarks, since it touches every
        evaluation, and its cost is measured against them.
      - Target: two tri-state buffers share one bus, and two drivers on
        at once show `X`.
   6. **A second reference CPU.**
      - The specification changes first (`docs/reference-cpu.md`): bit
        operations and a call and return, as Catch asked for.
      - Then its tests, then the circuit, as ADR 0020 item 3 requires.
      - Target: a version of Catch that draws single pixels and shares
        its drawing code.
3. **Rules from ADR 0020 item 3 still hold for every increment:**
   - behaviour stays in `sim-core`;
   - nothing leaves the browser;
   - an instruction set changes in its specification first;
   - each increment updates the roadmap and closes with a Playwright test
     of its target.
4. **Not planned in Phase 6.** These stay on the roadmap until a need
   shows:
   - several clocks;
   - stepping one delta;
   - project previews;
   - Markdown in notes;
   - global labels across sheets;
   - installing the app for offline use (PWA). The app would have to be
     served for this to matter, and deploying is not authorized.

## Alternatives considered

- **The richer CPU first.** It is the most visible, and a better Catch
  would show it off. But it changes no engine semantics and protects no
  one's work, and challenges 10 to 12 can use today's CPU. It goes last,
  where it can also use four-state buses if they help.
- **Four-state signals before the benchmarks.** They are a larger change
  to the engine. Measuring first means their cost is known rather than
  guessed, as brief §9 asks.
- **Editing while running before persistence.** Both stop work being
  lost. A reload or a closed tab loses everything since the last export,
  which is worse than an edit restarting the clock, and persistence also
  unblocks the challenge progress and component library that were already
  promised.
- **One increment for all the rough edges.** They touch unrelated code.
  Each joins the increment that works in its area, so it is tested with
  that work.
- **One ADR for all of Phase 6.** As ADR 0020 found, that freezes
  decisions before the work that informs them. This ADR fixes only the
  order and the targets; each increment's design is its own ADR.

## Consequences

- The next increment is local persistence, with its own ADR.
- The order can change between increments by amending item 2, as ADR 0020
  allowed.
- Each increment's target is concrete enough for a Playwright test, so
  "done" stays checkable.
- Benchmarks before four-state signals and the second CPU mean those two
  changes can show they did not slow the engine down.
