# 0022. Memory-mapped I/O on the reference CPU

- Status: Accepted
- Date: 2026-11-14
- Depends on: ADRs 0018 (ROM and RAM), 0019 (the reference CPU), 0020
  (Phase 5 plan, increment 2), 0021 (devices)

## Context

ADR 0020 makes memory-mapped I/O the second Phase 5 increment: the devices
of ADR 0021 decoded into the reference CPU's data address space, with no
new instructions. Target: a program reads the keyboard and writes the
screen.

The machine (`docs/reference-cpu.md`) has:

- 8-bit data and an 8-bit data address: `LDA n`, `STA n`, `ADD n` and
  `SUB n` reach `RAM[n]` for a 256-byte RAM;
- an `OUT` register driven by its own instruction, shown on an output
  device;
- no indirect addressing. The operand `n` is part of the instruction word,
  and the program is in a ROM, so a program cannot compute an address and
  then store to it.

The last point decides most of this ADR. A program that reads a key and
draws where that key says, or moves anything across a screen, needs an
address it computes at run time. With fixed operands only, a screen
mapped byte for byte into the data address space could be drawn only at
the places written into the program.

## Decision

1. **The top 16 data addresses are I/O.** `0xF0`–`0xFF` reach devices,
   not the RAM; `0x00`–`0xEF` (240 bytes) stay RAM. The decode is one
   test: the operand's top four bits are all 1. The RAM is still a
   256-byte part, but a store to an I/O address never writes it, and a
   load from one never reads it.

2. **Four devices, at fixed addresses.** They are reached by the existing
   `LDA`, `STA`, `ADD` and `SUB`.

   | Address | Name | Read (`LDA`, `ADD`, `SUB`) | Write (`STA`) |
   |---------|------|----------------------------|---------------|
   | `0xFF` | `KEY` | the keyboard's code: the key held, or 0 | ignored |
   | `0xFE` | `SPTR` | the screen pointer | `SPTR ← A` |
   | `0xFD` | `SDATA` | the screen byte at `SPTR` | that byte `← A` |
   | `0xFC` | `HEX` | the hex register | `HEX ← A` |
   | `0xF0`–`0xFB` | (reserved) | 0 | ignored |

   - **The screen pointer gives computed addresses without new
     instructions.** A program stores an address to `SPTR`, then loads or
     stores `SDATA`. Display chips have long worked this way: an address
     port and a data port. It has no auto-increment. That would be a
     write with a side effect, and a game can add 1 itself.
   - **The screen** is a 256-byte screen part (ADR 0021), so every
     pointer value is a byte on it. It is 64 pixels wide (`columns` 64,
     8 bytes a row) and 32 rows high. Byte `SPTR` is row `SPTR / 8`,
     pixels `8 × (SPTR mod 8)` onwards, most significant bit leftmost.
   - **`HEX`** drives two seven-segment digits through hex decoders, as
     in `devices.clockyard.json`. It shows a byte without a lookup table,
     which a program could not index anyway. The `OUT` register and its
     instruction stay as they are.
   - **`KEY`** is a level, not a queue. It reads the key held at that
     moment, and holding a key reads it again on every load. A program
     sees a new press by comparing with the code it read last. A latch
     cleared on read would need a read with a side effect, and nothing in
     the target needs one.
   - **`ADD` and `SUB` read devices** because they share `LDA`'s path to
     the data bus. The specification says so rather than adding a
     decoder exception.

3. **Timing and reset follow the existing rules.** A store to a device
   happens on the execute cycle's rising edge, as a RAM store does. A load
   reads the device during the execute cycle. Reset sets `SPTR`, `HEX`
   and every screen byte to 0. Once halted, no device register or screen
   byte changes. The keyboard is an input the editor sets, as a switch is
   (ADR 0021).

4. **The specification changes first** (ADR 0020 item 3):
   - `docs/reference-cpu.md` gains an I/O section with the table above,
     and says that data addresses `0xF0`–`0xFF` are not RAM.
   - The Rust reference model in `crates/sim-core/tests/cpu.rs` gains the
     keyboard as an input, the screen bytes, `SPTR` and `HEX`. The
     netlist and the model are compared after every cycle, as now. The
     random-program test also sets keyboard values, so loads from `KEY`
     are checked too.
   - Then the circuit, generated by `scripts/reference-cpu.mjs`. Its
     parts:
     - an I/O decoder on the operand;
     - the RAM's write enable gated off for I/O addresses;
     - `SPTR` and `HEX` as 8-bit registers like `OUT`;
     - the screen with its `addr` from `SPTR`;
     - a read multiplexer in front of `A` choosing RAM, `KEY`, `SPTR`,
       `SDATA` or `HEX`;
     - the keyboard, the two digits and their decoders.

   The keyboard, the screen and the digits go on the main sheet, where the
   keyboard can be clicked and the screen can be seen in the default view.

5. **The assembler is unchanged.** Programs write `0xFF` and the other
   addresses as numbers. Named constants (`KEY = 0xFF`) would read better,
   and the game increment can add them if it needs them. This increment
   changes no instruction, no encoding and no assembler syntax.

6. **Target program.** The example's ROM ships with a program that reads
   the keyboard, shows the code on the digits, and lights a byte on the
   screen at the code's address:

   ```
   loop:   LDA 0xFF     ; KEY
           JZ loop      ; no key held
           STA 0xFC     ; HEX: show the code
           STA 0xFE     ; SPTR: the code is the address
           LDI 0xFF
           STA 0xFD     ; SDATA: eight pixels on
           JMP loop
   ```

   Playwright runs it: it holds a key, then checks the digits and the
   screen's contents in its inspector (ADR 0021 step 4).

7. **Order of work.** Each step is one pull request:
   1. Specification, reference model, circuit and native tests. The
      circuit must match the model on the existing programs and on the
      new I/O ones.
   2. The device layout on the CPU sheet, the target program in the
      example, Playwright, and docs. This closes the increment.

## Alternatives considered

- **Indirect addressing instructions** (`LDX`/`STX` through a pointer
  register). They are the usual answer, and the game may want them
  anyway. But ADR 0020 asks for no new instructions in this increment,
  and the pointer port gives the same reach for the screen alone. If the
  game needs indirect RAM access, it gets an ADR then.
- **The screen mapped directly into the address space.** It is simpler to
  wire. But with fixed operands only, a program could draw only at the
  places written into it, so no key could move anything.
- **A smaller I/O window** (four addresses). It leaves no room for the
  game's devices without moving the boundary again. Sixteen costs 16 RAM
  bytes, and the decode is no harder.
- **I/O at the bottom of the address space.** Existing programs and tests
  use low RAM addresses (`STA 0`, `STA 1`), so moving them would change
  every example program. Programs rarely reach the top bytes.
- **A keyboard latch with "key ready".** It is better for typing text, but
  it needs a read with a side effect and a flag. A game polls the held
  key, which is what the target needs.

## Consequences

- Programs lose RAM bytes `0xF0`–`0xFF`. A program that stored data there
  now writes devices or nothing. The bundled programs use low addresses
  only, and the random-program test follows the new specification.
- The reference CPU can draw anywhere on a 64 × 32 screen, read keys, and
  show a byte in hex, with its instruction set unchanged. That is enough
  to start choosing the game (increment 3).
- The CPU sheet grows: a decoder, two registers, a read multiplexer and
  three devices. It is already dense (a roadmap rough edge), so step 2
  places the devices where the default view shows them.
- Reading `SDATA` lets a game test pixels, for collisions, without a copy
  of the screen in RAM.
